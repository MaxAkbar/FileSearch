Smart Search with ONNX

Search indexed text by meaning.

Smart Search uses a local ONNX embedding model to find related passages even when they use different words. You need a usable model pack and Smart Search vectors for the folder you are searching.

1. Select or Install a Model

Open File > Settings > Smart Search. The Local embedding model list offers BGE small English v1.5 and all-MiniLM-L6-v2; Disabled turns semantic search off.

Selecting a model starts its installation automatically. Install model also starts or retries installation. Wait for the installed model and successful smoke-validation status. Installation downloads model assets; embedding and retrieval then run locally without paid embedding services.

If the selected pack is already on disk, set Model folder to its parent model-packs directory and click Refresh to check it. The default parent is %LocalAppData%\FileSearch\Models. Keep the complete pack, including its vocabulary and any external ONNX weight files.

Have a standalone .onnx file? The current desktop UI selects the two catalog model packs; it has no arbitrary-ONNX import dialog. A bare file is not a complete text embedding setup: it also needs a compatible tokenizer, vocabulary, and model-pack configuration. Model folder is the parent of pack directories, not the path to an ONNX file.

After changing an already-loaded model or its folder, restart FileSearch and any running tray indexer before rebuilding vectors. Model sessions are retained for the lifetime of their process.

2. Build the Folder's Smart Search Index

  1. Open Index > Manage indexed locations and add the folder you want to search.
  2. Build its normal content index. Enable document extraction for Office, PDF, and mail; enable OCR before indexing if you need recognized image text.
  3. Select the location and open its Location details. Under Smart Search, click Rebuild Smart Search.
  4. Allow the background rebuild to finish, then click Refresh status. Look for Smart Search ready and vector coverage for the location.

Rebuild Smart Search creates vectors from existing indexed content without rebuilding the content index. If that content is missing or stale, first use Rebuild selected for the normal index. Installing a model alone does not make unindexed files searchable by meaning.

Vectors must match the selected model. After switching models, rebuild Smart Search for your locations. A drive file-name index supplies names only and cannot supply semantic document or mail content.

3. Run a Semantic Query

  1. Set the folder in the main search bar to the indexed location or a folder inside it.
  2. Click Semantic beside the .* regex toggle in the search box, or choose Semantic under Match in search options. This selects Contents and Use index automatically.
  3. Use the controls below the search box to set Minimum score and Maximum files. The defaults are 0.60 and 25 files. Click Search after changing them.
  4. Enter an ordinary phrase such as authentication migration and click Search. No query prefix is needed.
  5. Select a result card to read the cited source passage in the preview pane.

Semantic mode treats your entire input as the concept to search for, including quotes, punctuation, and words such as AND; it does not parse query fields or operators. It searches vector matches without a match-all file scan. Saved searches and workspace bundles remember the mode. Turning the toggle off returns to Unified mode; selecting regex, a file/folder-name target, or turning off Use index leaves Semantic mode.

The explicit semantic:"your concept" syntax remains available in Unified mode with Contents and Use index enabled. Ordinary words in other modes still perform lexical matching; selecting a model does not make every query semantic. Quick Search uses plain text and does not offer Semantic mode.

Understand the Results

Semantic retrieval supplies a ranked selection of related passages. It currently considers up to 25 file candidates and 50 semantic matches before result fusion. This is not an exhaustive count of every relevant passage; use literal, Boolean, or regex searches when you need exact terms.

Each file contributes its strongest semantic passage to the ranking, so a longer file does not rank higher just because it has more indexed chunks. In dedicated Semantic mode, Minimum score removes candidates below your chosen similarity score (0.00–1.00); a higher value is stricter. Maximum files returns the best 1–25 distinct files that meet that minimum. A result card shows its similarity score, rounded to two decimals; filtering uses the full score. These are model-dependent similarity scores, not probabilities or confidence percentages.

Start at 0.60, then raise the minimum if weak matches remain or lower it if relevant matches disappear. For example, in the docs test with BGE small English v1.5, Determines whether filename/path search feels instant returned four documentation files at 0.60 and only BENCHMARKS.md at 0.70, excluding the license files. A broad word such as query scored lower, so it required a minimum around 0.58 to return BENCHMARKS.md. More specific phrases usually give a clearer ranking. Use 0.00 to inspect the full candidate selection. No index rebuild is needed when changing these controls.

The controls are remembered across sessions, saved searches, and workspace bundles. They apply to the dedicated Semantic mode; advanced semantic: queries in Unified mode retain their existing candidate limits and do not use these controls.

Why an Unrelated Passage Can Still Appear

Semantic search can return false positives: passages that score above your minimum but do not address the concept you meant. A similarity score measures the embedding model's similarity between the query and indexed text; it does not verify that a passage answers the query. Minimum score filters those scores, and Maximum files caps the result count. Neither control guarantees that every returned passage is relevant.

For example, searching the eight-file docs test index with BGE small English v1.5 for query breakdown returned these two leading results:

ResultSimilarity scoreRelevance to the phrase
BENCHMARKS.md, line 320.647Directly explains the indexed query phase breakdown: database open, metadata lookup, trigram lookup, row fetch, and recheck.
IFILTER_VALIDATION.md, line 220.603A false positive: discusses reducing a third-party extractor's timeout, not breaking down query processing.

The default minimum of 0.60 admits both. A minimum of 0.62 retains only BENCHMARKS.md for this example. That cutoff is not a universal relevance threshold: scores vary with the model, query, and indexed content, and raising it can also remove useful matches. Preview the matched passage, adjust the minimum, and click Search again. For exact occurrences of words or phrases, use plain text, Boolean, or regex matching instead.

In Unified mode, combined results can include metadata or lexical candidates too; a displayed item does not necessarily come from vector similarity. The dedicated Semantic mode uses vector candidates only. Result fusion currently groups candidates by physical file, so semantic results from a PST/OST can show only a selected message from that store.

The semantic provider scopes vectors to the selected search roots, but does not consistently apply Unified type/path/date/size fields or the scan's file filters to semantic candidates. Choose a specific indexed folder to narrow the search and use result facets to refine visible items. Do not rely on a combined type:pdf semantic:... query as a strict file-type restriction.

Local reranker in Settings applies a local heuristic ranking pass after result fusion in other search modes; it does not install a second ONNX model. Dedicated Semantic mode preserves vector relevance without keyword, filename, or hit-count bonuses. Preview the source text to judge whether a match answers your question. Answer creates an extractive draft from visible results rather than generating new facts.

If Smart Search Does Not Work

  • No results met the minimum score: lower Minimum score or use a more specific phrase, then click Search. This message means similarity filtering rejected the candidates; it does not mean the index needs rebuilding.
  • Unrelated passage above the cutoff: review the source passage and raise Minimum score if needed. The model can assign an irrelevant passage enough similarity to pass the cutoff; see the query breakdown example. Rebuilding an unchanged index with the same model does not improve that relevance judgment.
  • Model missing or not ready: check the selected model, parent model folder, vocabulary, external weights, and installation/validation status. Retry Install model for incomplete packs.
  • No vectors or partial coverage: check the location's Smart Search status. Wait for pending work or use Rebuild Smart Search. A usable model without indexed vectors cannot return semantic matches.
  • Content index read errors: Smart Search builds vectors from the content index. If that database cannot read its indexed rows, fix or recover the content index before rebuilding Smart Search. Check the location's status and the GUI log in %LocalAppData%\FileSearch\logs. Back up the existing index database before resetting it; it can contain other indexed locations too.
  • Wrong search setup: select Semantic in the main window and search inside the indexed location. It enables indexed content search automatically. An explicit semantic: query instead needs Unified mode, Contents, and Use index.
  • Changed model or initialization failure: restart FileSearch and any tray indexer, then rebuild vectors with the selected model.
  • Unavailable query chip: the current query parser can label a semantic chip Unavailable even when the model is installed. Check model and vector status; that chip label alone does not confirm runtime availability.
  • CLI query returns no semantic matches: the current CLI search process does not load the GUI's selected model configuration. The desktop main window is the documented Smart Search entry point.

Local Storage

Model assets are kept in the configured model folder. Semantic vectors are stored beside the content database in %LocalAppData%\FileSearch\Index\filesearch.vectors.json and filesearch.vectors.segments. Selecting Disabled stops semantic search; model and index files remain on disk.
